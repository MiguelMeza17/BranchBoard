# BranchBoard — Arquitectura

> Ver visión general en [PLANNING.md](./PLANNING.md). Este documento es una vista de pájaro de cómo encajan las piezas del sistema — para el detalle de cada comando/tabla, ver [BACKEND.md](./BACKEND.md) y [FRONTEND.md](./FRONTEND.md).

## Tipo de arquitectura

**Aplicación de escritorio con servidor central** (Fase 1, migración #231). React y el backend Rust se empaquetan en Tauri y se comunican por comandos IPC. Rust trabaja sobre SQLite local y habla por HTTPS con Supabase: Auth, Postgres con RLS, Storage y dos Edge Functions. La webview no se conecta directamente a internet. La Fase 2 (versión web, futura) podrá reutilizar ese servidor; no es necesaria para la sincronización actual.

## Componentes

- **Frontend**: React + TypeScript, corriendo dentro de la webview de Tauri. Renderiza las pantallas (actualizado 2026-11-07: apartado del proyecto con documentos, Chat, Tablero Scrum, Lista de tareas, Planificación, Categorías, Revisión, Resumen, Avance, Pendientes, Reportes, Branches, Usuarios, Papelera, Ajustes, más el acceso al proyecto y el perfil) y dispara acciones vía `invoke(...)` hacia el backend. **Es la referencia**: el mockup de `app/frontend/` define lo que el backend tiene que hacer (ver [Contrato con el frontend en BACKEND.md](./BACKEND.md#contrato-con-el-frontend-acciones-y-comandos)).
- **Backend**: Rust, dentro del mismo proceso de Tauri. Expone comandos que el frontend invoca (`tomar_tarea`, `aprobar_tarea`, `hacer_checkin`, `traer_cambios`, etc.), valida permisos por rol, y es el único que toca SQLite y `cm`.

- ~~**Bot clasificador (a futuro)**~~: **descartado (2026-11-02)**. Solo hacía falta para decidir el tipo de las tareas que nacían de un check-in; ya no existen tareas de check-in (ver [BACKEND.md](./BACKEND.md#check-ins-de-la-rama-subtarea-en-espera-y-cambios-entrantes)).
- **Persistencia (SQLite + Supabase, #244)**: cada PC conserva su base. Las mutaciones se aplican y encolan en una transacción; la bandeja publica y la recepción aplica por orden del servidor sin repetir ids. No se lee ni escribe `ops/`. Documentos e imagen usan Storage; sin vincular se pide subir el proyecto. La carpeta antigua solo se lee para migrar (#245). Ver [BACKEND.md](./BACKEND.md#sincronización-entre-máquinas-arquitectura-de-eventos).
- **Unity Version Control (vía `cm`)**: el backend invoca el CLI `cm` como subproceso para todo lo que toca ramas/changesets (crear rama, checkin, merge, leer historial). Es la fuente de verdad del código y los assets versionados — SQLite solo guarda referencias (nombre de rama, último changeset visto), nunca el contenido.
 BranchBoard **escucha Unity VC todo el tiempo** mientras está abierta (proceso de fondo): los check-ins hechos desde Unity y los cambios de rama del workspace se reflejan solos (ver [Detección de cambios en BACKEND.md](./BACKEND.md#detección-de-cambios-en-unity-version-control-polling)).
- **Gluon (workspace parcial)**: variante liviana de `cm` para colaboradores externos sin el proyecto completo instalado — mismo mecanismo de invocar subprocesos, solo que con `cm partial` en vez de los comandos normales.
- **Cloudflare WARP**: dependencia externa opcional, gestionada desde la app (`warp-cli`), necesaria cuando la red bloquea la conexión a Unity VC.

## Decisiones de arquitectura ya tomadas

- **Identidad común en Supabase Auth** (#236/#237): correo y contraseña o sesión de Unity VC validada por `login-unity`; el mismo correo corresponde a la misma cuenta. `cm whoami` identifica la sesión de Unity para las operaciones de su workspace; no es el login de todos los usuarios de BranchBoard. Los tokens de Supabase y los PAT de Unity se guardan en el llavero del sistema. El registro no confirma el correo por la enmienda de #236; el riesgo y la recuperación de contraseña pendiente se describen en [SEGURIDAD.md](./SEGURIDAD.md#reglas-del-servidor-supabase-234).
- **Actualizaciones por Releases de GitHub** (2026-11-09): un solo instalador para todos; la app se actualiza desde Ajustes, verificando la firma de cada versión — ver [Actualizaciones de la app en BACKEND.md](./BACKEND.md#actualizaciones-de-la-app).
- **Supabase central del dueño de BranchBoard** (decisión 2 de #231): los equipos comparten el servidor y se separan por proyecto y membresía. Las Edge Functions validan la identidad de Unity y al primer Administrador; las funciones SQL controlan los roles. La app solo incluye URL y clave pública. La API REST de Unity VC se sigue usando desde Rust con el PAT personal; `cm` y Gluon actúan sobre el workspace.
- **SQLite local y eventos compartidos en Postgres**: cada mutación se aplica y encola en una transacción. Rust sube la bandeja y consulta nuevos eventos cada ~5 s, ordenados por el servidor, sin reaplicar ids. Realtime queda para después (#239). Los roles se leen de `miembros` y solo cambian por funciones autorizadas; no viajan como eventos. Drive, `ops/` y las firmas de roles se retiraron (#243/#244); la carpeta antigua solo sirve para importar al servidor (#245).
- **Permisos repartidos entre Rust y el servidor**: Rust valida las acciones locales. RLS separa proyectos y controla el acceso a eventos y archivos; las funciones SQL validan los cambios de equipo y el último Administrador. La inserción de eventos comprueba membresía, autor y permisos por **tipo** (#247); no valida todas las reglas de negocio del payload. Los permisos de Unity siguen siendo independientes: las reglas sobre ramas de BranchBoard no impiden operaciones directas desde Plastic. Ver [SEGURIDAD.md](./SEGURIDAD.md#reglas-del-servidor-supabase-234) y [Protección de ramas en BACKEND.md](./BACKEND.md#protección-de-ramas-main-y-dev).
- **Comandos externos siempre por subproceso con argumentos separados**, nunca por string de shell — ver [Seguridad al invocar cm en BACKEND.md](./BACKEND.md#seguridad-al-invocar-cm-evitar-inyección-de-comandos).

**Pendientes de #231**:

- Conectar Usuarios a los comandos del servidor y comprobar invitaciones, cambios de rol y revocación desde Tauri. Quitar una fila del store no revoca membresía ni acceso a Storage; una invitación visual no incorpora a nadie al proyecto.
- Completar la decisión 8 para los proyectos del servidor ([#277](https://github.com/MiguelMeza17/BranchBoard/issues/277)) y comprobar una exportación/restauración con documentos en `branchboard-pruebas`. Los backups locales de SQLite no contienen por sí solos los archivos de Storage.

El cierre de las tareas de migración no demuestra que estos dos flujos estén completos. Esta revisión no cambia las decisiones ni da por terminado ese alcance.

**Despliegue comprobado (2026-11-21)**: producción tiene las nueve migraciones hasta `20261122100000` y las dos Edge Functions (`login-unity`, `vincular-repo-unity`) activas. Se verificaron permisos y respuestas sin crear datos de prueba en producción. Las pruebas funcionales se realizan en `branchboard-pruebas`; desplegar no sustituye la prueba de exportación que falta.

**Validación del cotejo**: 139 comprobaciones SQL pasan en `branchboard-pruebas` (reglas y roles: 65; funciones de Unity: 15; alta offline: 8; Storage: 27; invitaciones: 24), en transacciones que se deshacen al terminar. La lectura pública de `/auth/v1/settings` confirma registro por correo activo y `mailer_autoconfirm: true` tanto en pruebas como en producción. Estas comprobaciones validan el servidor, no los dos flujos de interfaz que faltan.
